Meshi v1.101

Architecture & Reliability Improvements — May 1, 2026 — Base: v1.100 (build 30)

This release focuses on internal architecture improvements: thread-safety, retry logic for BLE operations, input validation on mesh data, centralised configuration, and splitting oversized classes into focused components. No UI changes — all improvements are under the hood.

High Priority Changes

High

1. Thread-Safety on Shared Mutable State

Problem:

pendingAcks, pendingPings, and typingJobs were plain mutableMapOf() instances accessed from multiple coroutines without synchronisation — a data race waiting to happen.

Fix:
  • pendingAcks and pendingPings in FrameRouter now use ConcurrentHashMap
  • typingJobs in ChatViewModel now uses ConcurrentHashMap
  • contactsAccumulator in FrameRouter is guarded by synchronized blocks
High

2. Retry Logic with Exponential Backoff

Problem:

Failed BLE sends surfaced an error immediately with no retry. On a mesh network where transient failures are common, a single failure doesn't mean the operation can't succeed.

Fix:

New withBleRetry() utility:

  • Attempts the operation once
  • On failure, retries up to 3 times with exponential backoff (500ms → 1s → 2s)
  • Applied to all send operations: direct messages, channel messages, game protocol, pings, login, channel management
High

3. Input Validation on Received Mesh Data

Problem:

Data arriving from the mesh is untrusted. Contact names, message text, GPS coordinates, and channel info were passed directly to the UI and database without validation.

Fix:

New InputValidator object applied at the protocol boundary in FrameRouter:

ValidatorWhat it does
sanitizeName()Strips control characters, trims whitespace, enforces 32-char max
sanitizeChannelName()Same rules for channel names
sanitizeMessageText()Strips control characters (preserves newlines), trims
isValidPubKeyPrefix()Checks length ≥ 6 bytes and not all zeros
isValidGps()Validates lat ∈ [-90, 90] and lon ∈ [-180, 180]
isValidChannelIdx()Validates index ∈ [0, 7]
High

4. Centralised Configuration Constants

Problem:

Magic numbers scattered across the codebase — timeouts, limits, thresholds, and intervals required hunting through multiple files to change.

Fix:

New MeshiConfig object with all constants in one place:

object MeshiConfig {
    const val HANDSHAKE_DEVICE_QUERY_TIMEOUT_MS = 6_000L
    const val SEND_MAX_RETRIES = 3
    const val SEND_RETRY_BASE_DELAY_MS = 500L
    const val MESSAGE_MAX_LENGTH = 160
    const val ADVERTS_MAX_SIZE = 50
    const val ADVERTS_TTL_MS = 30 * 60 * 1000L
    const val TYPING_INDICATOR_TTL_MS = 5_000L
    const val SOS_ADVERT_INTERVAL_MS = 30_000L
    const val DEFAULT_BATTERY_ALERT_PCT = 20
    // ... and more
}

Referenced from BleManager, MeshRepository, ChatViewModel, MeshiForegroundService, FrameRouter, and SosManager.

Medium Priority Changes

Medium

5. ChatViewModel Split — Game Invite & SOS Extraction

Problem:

ChatViewModel was ~400 lines handling messaging, game invites for 4 games, SOS beacon management, typing indicators, reactions, search, and more.

Fix:

Extracted two focused managers:

  • GameInviteManager — Listens to game messages, routes invites (Reversi, Chess, TicTacToe, Battleship) to per-game StateFlows, provides clear methods
  • SosManager — Manages the repeating flood advert loop, persists state to AppPreferences, resumes on restart, respects stealth mode

ChatViewModel delegates to both, removing ~80 lines of inline logic.

Medium

6. MeshRepository Split — Frame Router Extraction

Problem:

MeshRepository was ~500 lines handling both frame dispatch (the large when(frame) block) and send/command operations.

Fix:

Extracted FrameRouter class that owns:

  • The entire handleFrame() dispatch with all frame types
  • Direct message routing (game protocol, reactions, typing, regular messages)
  • Channel message routing and advert processing
  • Contact list accumulation during sync
  • Thread-safe delivery confirmation (ack/ping) tracking
  • All SharedFlow emissions for game messages, typing events, reactions, pings, and login results

MeshRepository now focuses on send operations, scan control, and state exposure (~150 lines removed).

Medium

7. Advert TTL (Time-to-Live)

Problem:

The advert list kept the last 50 entries but never expired old ones. Adverts from nodes that went offline hours ago remained visible.

Fix:
  • Added timestampMs field to AdvertEvent
  • FrameRouter.addAdvert() filters out adverts older than 30 minutes before adding new ones
  • Combined with the existing max-size cap of 50
